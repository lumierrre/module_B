# Модуль B — анализ защищённости банковского микросервиса

## 1. Моделирование угроз

### 1.1. Назначение системы и область анализа

Рассматриваемый сервис предоставляет два метода REST API: проведение перевода между счетами (`POST /transfer`) и получение списка транзакций (`GET /transactions`). Основные защищаемые активы — остатки на счетах, записи о денежных операциях, сведения о принадлежности счетов и реквизиты подключения к хранилищам.

Для оценки безопасности используется STRIDE. Модель подготовлена в формате OWASP Threat Dragon v2. Исследование ограничено исходным кодом и конфигурацией Docker Compose; эксплуатация уязвимостей на работающем сервисе не проводилась. Изменения в исходники не вносились.

Материалы моделирования:

- [Модель угроз в JSON](threat_dragon_model.json) — для открытия в OWASP Threat Dragon.
- [Отчёт с диаграммой и обоснованием угроз](threat-dragon-report.pdf) — PDF, сформированный отдельно от Threat Dragon. Нативный экспорт необходимо получить в самом приложении после проверки импорта модели.

### Архитектура и DFD

В модели выделены четыре элемента: внешний клиент, процесс обработки HTTP-запросов (FastAPI), постоянное хранилище (PostgreSQL) и вспомогательное хранилище (Redis). Клиент не должен обращаться к хранилищам напрямую: обработка запросов и контроль доступа должны осуществляться через Backend API.

| Канал | Запрос (поток) | Ответ (поток) |
|---|---|---|
| Клиент ↔ FastAPI | F1: `X-User-Id`, параметры перевода, `limit`, `search` | F2: статус операции, ID транзакции, история, сообщения об ошибках |
| FastAPI ↔ PostgreSQL | F3: чтение остатков и владельцев счетов, изменение баланса, запись транзакции | F4: результаты SQL-запросов, идентификаторы и сведения об операциях |
| FastAPI ↔ Redis | F5: чтение ключа истории (`GET`), удаление ключа после перевода (`DEL`) | F6: содержимое или отсутствие ключа, результат удаления |

Redis в исследуемой реализации не является источником финансовых данных. Механизм записи истории в кеш отсутствует, хотя в коде присутствуют операции чтения и инвалидации.

**Границы доверия:**

- TB1 отделяет внешнего HTTP-клиента от серверной части. Все сведения, поступающие от клиента, включая идентификатор пользователя, необходимо считать недоверенными до проверки.
- TB2 разделяет прикладной уровень и уровень хранения данных. Доступ к PostgreSQL и Redis должен быть ограничен компонентами, которым он необходим для работы.

Эти границы отражают логическое устройство системы, а не гарантированную сетевую изоляцию. В `docker-compose.yml` опубликованы порты 8000, 5432 и 6379. Доступность последних двух извне зависит от настроек сети и межсетевого экрана. Явная настройка TLS в предоставленной конфигурации отсутствует.

### 1.2. Определение приоритетов

При выборе угроз учитывались доступность потенциальной точки атаки, объём затрагиваемых данных и последствия для денежных операций. Приоритет получили сценарии, которые способны нарушить контроль доступа, корректность расчётов или сохранность финансовой информации.

| Код | Сценарий | Категория STRIDE | Вероятность | Ущерб | Балл |
|---|---|---|---:|---:|---:|
| T01 | Действия от имени другого клиента | Spoofing / Information Disclosure | 5 | 5 | **25** |
| T02 | Некорректный остаток при конкурентных переводах | Tampering | 4 | 5 | **20** |
| T03 | Доступ к финансовому хранилищу в обход API | Information Disclosure / Tampering | 4 | 5 | **20** |

Балл риска представляет собой произведение вероятности (L) и тяжести последствий (I). Оба параметра оцениваются по пятибалльной шкале. Значение 5 соответствует максимальной вероятности или ущербу, значение 1 — минимальным. Оценки экспертные, не являются CVSS и предполагают работоспособное приложение. Для T03 дополнительно предполагается сетевая доступность БД.

| Итоговый балл | Интерпретация |
|---|---|
| 1–4 | Низкий |
| 5–9 | Средний |
| 10–19 | Высокий |
| 20–25 | Критический |

В модели Threat Dragon для трёх сценариев используется severity High; числовая шкала позволяет отдельно отразить критичность для банковского бизнеса.

### T01 — Нарушение доверия к идентификатору клиента

**Компонент:** Backend API. **CWE:** CWE-306, CWE-639.

**Основания в исходном коде:** `app/security.py:3–13`, `app/main.py:13–24`, `app/crud.py:5–16, 43–66`.

Функция определения текущего пользователя принимает идентификатор из HTTP-заголовка `X-User-Id`. Обработчик проверяет наличие значения и возможность его преобразования в целое число, но не устанавливает подлинность клиента. Проверки владельца счёта и выборка истории транзакций используют полученный таким образом идентификатор.

Следовательно, проверка принадлежности объекта существует, однако опирается на недоверенную идентичность. Это делает возможным нарушение объектного контроля доступа (IDOR/BOLA) вследствие отсутствия полноценной аутентификации.

**Поверхность атаки:** оба публичных метода API и зависимость, определяющая текущего пользователя.

**Последствия для банка:** несанкционированное раскрытие истории операций, распоряжение чужими средствами, нарушение банковской тайны и расходы на урегулирование спорных переводов. Риск получил максимальный балл, поскольку затрагивает обе основные функции сервиса и не предполагает предварительный захват хранилища.

**Предлагаемая защита:**

| Уровень / тип | Защитная мера | Ожидаемый результат |
|---|---|---|
| Код / техническая | Получать идентификатор из проверенного токена; валидировать подпись JWT, issuer, audience и срок действия | Исключение доверия к произвольному идентификатору |
| Код / техническая | Проверять права аутентифицированного субъекта на конкретный счёт и историю операций | Предотвращение межпользовательского доступа |
| Инфраструктура / архитектурная | Централизованный IdP, API Gateway, TLS и запрет прямого обхода шлюза | Формирование доверенного контура идентификации |
| SDLC / процессная | Проверка модели авторизации на code review и негативные тесты с двумя клиентскими аккаунтами | Обнаружение регрессий контроля доступа до релиза |

### T02 — Нарушение финансовых инвариантов при параллельной обработке

**Компоненты:** FastAPI и PostgreSQL. **CWE:** CWE-362.

**Основания в исходном коде:** `app/crud.py:20–38`, `app/db.py:15–29`.

В ходе перевода сервис сначала получает остаток на счёте, затем сравнивает его с суммой операции и после этого выполняет списание. Чтение и изменение остатка не объединены атомарным условием, блокировка строки на этапе чтения отсутствует.

Даже при использовании транзакции PostgreSQL две конкурентные операции могут пройти проверку достаточности средств по одному исходному остатку. Дополнительное ограничение неотрицательного баланса в определении таблицы также отсутствует.

**Поверхность атаки:** метод `POST /transfer` и конкурентная работа транзакций базы данных. Проблема может возникать не только вследствие злоумышленных действий, но и при обычной параллельной нагрузке.

**Последствия для банка:** списание сверх доступной суммы, отрицательные остатки, расхождения при сверке и финансовые потери. Высокий ущерб обусловлен нарушением базового требования к платёжной системе — корректности движения средств.

**Предлагаемая защита:**

| Уровень / тип | Защитная мера | Ожидаемый результат |
|---|---|---|
| Код и БД / техническая | Атомарное условное списание с проверкой результата либо блокировка записей в согласованном порядке | Исключение гонки между проверкой и списанием |
| Код / техническая | Ключ идемпотентности для денежных операций | Защита от отдельного смежного риска — повторного исполнения запроса |
| БД / архитектурная | Ограничения CHECK, внешние ключи и сохранение единой ACID-транзакции | Поддержание целостности балансов и записей об операциях |
| SDLC / процессная | Конкурентные тесты, проверка остатков и сверка суммы средств до и после операций | Контроль финансовых инвариантов при изменениях бизнес-логики |

### T03 — Компрометация постоянного хранилища

**Компонент:** PostgreSQL. **CWE:** CWE-798, CWE-284.

**Основания в конфигурации:** `docker-compose.yml:6–11, 20–24`.

В конфигурационном файле заданы учётные данные привилегированного пользователя PostgreSQL. Те же реквизиты использует приложение при установлении соединения. Порт 5432 опубликован на хосте, поэтому при наличии сетевой доступности существует возможность обращения к СУБД вне штатного интерфейса приложения.

**Поверхность атаки:** сетевой интерфейс PostgreSQL, конфигурация контейнеров и параметры подключения приложения.

**Последствия для банка:** массовое раскрытие сведений о счетах и транзакциях, изменение или уничтожение финансовых записей, недоступность истории и остановка переводов. В отличие от нарушения доступа к отдельному счёту, компрометация БД способна затронуть весь массив клиентских данных. Вероятность оценена ниже максимальной, поскольку фактическая доступность порта извне не установлена.

**Предлагаемая защита:**

| Уровень / тип | Защитная мера | Ожидаемый результат |
|---|---|---|
| Инфраструктура / техническая | Ротация реквизитов и хранение секретов вне репозитория | Снижение риска использования раскрытых паролей |
| БД / техническая | Выделенная роль приложения с минимальными правами | Ограничение масштаба ущерба при компрометации приложения |
| Инфраструктура / техническая | TLS для соединений с СУБД | Защита данных и реквизитов при передаче |
| Инфраструктура / архитектурная | Приватная сеть, отсутствие ненужной публикации порта и сетевые ACL | Блокирование прямого доступа к БД вне доверенного контура |
| SDLC / процессная | Secret Scanning, проверка Docker Compose и сетевой доступности перед выпуском | Предотвращение повторного появления опасных настроек |

Сходный сетевой риск относится и к Redis: порт 6379 опубликован, а аутентификация в предоставленной конфигурации явно не задана. Он учитывается при проектировании изоляции хранилищ.

### Дополнительная проверка SQL Injection

В описании задания SQL Injection указана как ожидаемая уязвимость. Однако анализ `app/crud.py:52–66` не подтверждает её в предоставленной версии репозитория: динамическая сборка SQL используется для формирования номеров параметров, тогда как значение `search`, идентификатор пользователя и `limit` передаются в `asyncpg` отдельно от текста запроса. Совпадение с правилом поиска динамического SQL следует рассматривать как кандидат на ручную проверку, а не как доказанную SQL-инъекцию.

### Ограничения и заключение

Главные риски распределены между тремя уровнями системы: входным интерфейсом, логикой обработки платежей и постоянным хранилищем. Первым приоритетом является восстановление доверенной идентификации клиента и контроля прав на объекты, следующим — обеспечение атомарности денежных операций и ограничение доступа к базе данных.

Все три угрозы остаются открытыми (Open). Контрмеры предложены, но не реализованы. Наличие несовпадающих имён импортируемых функций и моделей (`app/main.py:3–4`, `app/security.py:3`, `app/schemas.py:3, 8`) препятствует штатному запуску представленного приложения; выводы описывают риски исходного кода, а не результаты динамической эксплуатации. Импорт модели в Threat Dragon и штатный экспорт PDF в доступной среде не проверены.
